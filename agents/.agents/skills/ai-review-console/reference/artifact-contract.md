# AI Review Console — Artifact Contract

The whole pattern rests on a small, well-defined set of artifacts. Keeping each
one's shape stable is what makes the console reusable across domains — the same
generator handles a Todoist reconciliation, a transaction review, an inbox
triage, or a content backlog, because none of them are hardcoded into the code.

## The pipeline

```text
deterministic data script → agent-authored review spec → static HTML console
    → human exports decision JSON → safe apply pass
```

Four artifacts matter:

1. **Deterministic data (JSON)** — the facts. Produced by a read-only script
   that snapshots the current state of whatever system is being reviewed.
2. **Agent-authored review spec (JSON)** — the questions. Written/edited by an
   agent to frame what the human should decide this time.
3. **Static HTML console** — the surface. Generated by `review_console.py` from
   data + spec. Read-only; captures decisions.
4. **Decision JSON** — the approval artifact. Exported by the human from the
   console; consumed by the apply pass.

## 1. Deterministic data JSON

Shape (top level):

```json
{
  "date": "2026-08-01",
  "counts": { "queue_source": 3, "other_queue": 1 },
  "<queue_source>": [ { "item": "..." }, { "item": "..." } ]
}
```

Rules:

- **Read-only by default.** The data script must not mutate the underlying
  system. It snapshots current state.
- **Deterministic enough to re-run.** Same inputs → same (or near-same) output,
  so a review can be regenerated safely.
- **Explicit source records.** Every item should carry whatever identifiers let
  the apply pass find it again (`id`, `path`, `url`, shared keys, etc.).
- **Capture enough raw data for safe apply.** The console embeds each item's raw
  JSON so a decision references exactly the state it was made against.
- **No LLM-only inferred state as the sole evidence.** The data script should be
  factual; subjective classification belongs in the spec/questions, not the data.

The top-level keys a spec's queues reference via `source` become the review
queues. `counts` values are just surfaced as metadata chips in the header.

## 2. Agent-authored review spec JSON

This is where judgment lives — not in the data collection. The spec controls:

- `title`, `subtitle`, `agent_note` — framing shown to the human.
- `global_actions` — fallback actions available on every card (e.g. defer,
  needs-human-decision, ignore).
- `queues` — one per review group:
  - `id` — stable slug, also becomes the in-page anchor.
  - `title`, `description` — what the queue is and why it matters.
  - `source` — key in the data JSON this queue reads from.
  - `empty` — message when the queue has no items.
  - `detail_keys` — which item fields render as metadata cards.
  - `primary_keys` — which of those get visually emphasized (status/priority/
    due-style fields).
  - `actions` — the decisions for this queue; each is `{ "id", "label" }`.

An agent writes a fresh spec per review task so the UI matches the question.
The generator is intentionally NOT the intelligence.

## 3. Static HTML console

Generated by:

```bash
python3 review_console.py --data review-data.json --spec review-spec.json --out Review.html
```

Properties:

- **Works offline as a single file.** No build step, no server, no network.
- **Read-only toward external systems.** The page never calls Todoist,
  Obsidian, an API, or a server. It only records in-browser choices.
- **Stores decisions in `localStorage`** when the viewer permits it; falls back
  to in-memory session decisions when a viewer (Telegram, some iOS/file
  viewers) blocks storage. A status badge tells the human which mode is active.
- **Export surface:** preview, copy (with clipboard fallback), and download.
  Download name is `<slug>-decisions-YYYY-MM-DD.json` where `<slug>` derives
  from the console title.
- **Storage isolation:** the `localStorage` key includes a slug of the console
  title, so two different consoles on the same origin don't collide.

## 4. Decision JSON (exported approval artifact)

```json
{
  "console_title": "My Review",
  "exported_at": "2026-08-01T12:00:00.000Z",
  "decisions": [
    {
      "id": "<source>:<item-id>",
      "queue": "<queue-source>",
      "action": "approve",
      "label": "Approve",
      "note": "optional rationale",
      "item": { "...raw item snapshot..." },
      "decided_at": "2026-08-01T11:30:00.000Z"
    }
  ]
}
```

This file is the contract with the apply pass. It says exactly which item, which
queue, which action, with the raw state it was decided against, and any note the
human added. Treat it as a durable approval record, not a throwaway.
